# Security

This is financial software. Defaults are the safe choice.

| Area | Implementation |
|---|---|
| Sign-in | Laravel session auth via Sanctum (first-party cookie, `SameSite=Lax`, HttpOnly, encrypted session payload), session id regenerated on login, cookie `tradepilot_session`. Public sign-up (`POST /api/auth/register`, 10 per hour per IP; disable with `TP_REGISTRATION_ENABLED=false`): password 10+ chars, mixed case, a number; the risk disclosure must be accepted. `php artisan tp:user` creates users (and the first admin) from the command line. |
| MFA | TOTP (RFC 6238) + 8 single-use recovery codes (stored hashed, encrypted). The session is authenticated only **after** the code. Codes can't be replayed. The code step is limited per pending user + IP (5 / 15 min, so a new session does not reset it), and 5 wrong codes in 15 minutes lock that user's code step for 15 minutes whatever the IP (audited as `auth.mfa.locked`). Always required to enable LIVE. `TP_REQUIRE_MFA=true` forces enrolment for everyone. |
| Account enumeration | Login gives the same answer and costs the same password-hash check for unknown emails; sign-up answers a taken email with a generic "We couldn't create an account with these details." |
| CSRF | Laravel's `XSRF-TOKEN` cookie echoed in `X-XSRF-TOKEN` on every state-changing request. |
| Authorization | Roles `user` and `admin`. Every record has an owner; indexes are scoped to the current user and policies per model (`app/Policies`) refuse another user's record (403/404). Admins can read any record by id but can't trade or modify other users' accounts, run or copy another user's private strategy, or query a broker through another user's connection (the `use` ability: owner or shared records only). The `operate-platform` gate (admins) covers the platform halt and the Horizon dashboard. Audit log: users see their own actions, admins see all. |
| Rate limiting | Sign-up (10 / hour per IP), login (5 per email / 15 min, counting failures and correct passwords still waiting for the MFA code; plus 50 per IP / 15 min; configurable), MFA (5 / 15 min), trading actions (30/min), broker actions incl. history downloads (12/min), plain-English strategy drafts (10/hour per user), API (300/min). STOP TRADING and Close positions have their own budget (30/min per user) outside the API limit, so polling can never block them. Client IPs come from `X-Forwarded-For` of `TRUSTED_PROXIES` only — see [DEPLOYMENT.md](DEPLOYMENT.md#client-ip-addresses-and-proxies). |
| Validation | Form requests / validator rules for every input; the engine validates again with Pydantic. A stop loss is always required. |
| Broker secrets | AES-256-GCM with `BROKER_CREDENTIALS_KEY` (separate from `APP_KEY`), stored only as ciphertext, decrypted only inside the engine, hidden from every serialisation, never logged, never in frontend bundles. Archiving a broker wipes them. Deriv OAuth tokens never reach the browser. |
| Engine API | Bound to 127.0.0.1, every request HMAC-SHA256-signed over method, path+query, timestamp, nonce and body hash; 60-second window; nonces can't be replayed. |
| Audit log | Append-only (MySQL triggers refuse UPDATE/DELETE). Every security and trading action, allowed or refused, with actor, IP, user agent and masked details. |
| Logs | Secret keys/values masked in Laravel audit details and in engine logs (`password`, `token`, `secret`, `authorization`, …). Request input with secrets is never flashed. |
| Headers | `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Cache-Control: no-store` on API responses; CSP `frame-ancestors 'none'` on the dashboard; HSTS over HTTPS. |
| LIVE | `LIVE_TRADING_ENABLED=false` by default in both services. Per user, LIVE mode also needs their trading stopped, MFA, password, the typed phrase and one of their LIVE accounts with a risk profile (the authorisation time, that account, its profile and a snapshot of its limits are recorded; switching back to DEMO clears it). The engine trades a LIVE account only if it is that account, still on that profile, and the profile was not edited since. Authorisation is **revoked** (back to DEMO, the user's trading stopped, a notification and an audit record saying why) when the profile is edited, the account's profile changes, the account's trading is switched off and on again, another LIVE account is added, MFA is turned off or the password changes. Starting trades in LIVE mode needs `live: true` from the dashboard, so a stale "Demo" dialog can't start real-money trading. LIVE mode trades LIVE accounts only; LIVE accounts can't have trading enabled while locked; UNKNOWN accounts never trade. |
| AI drafting | Optional (`ANTHROPIC_API_KEY` on the engine only). The user's description is **untrusted input**: sent to Anthropic inside delimiters with an instruction that it is data, never instructions; it never enters the (cached) system prompt. The model can only answer with JSON in a fixed schema built from the rule catalogue — rule sets are declarative data, **no code is ever executed or evaluated**. Every draft is re-validated by the same validator as builder rules, is never saved automatically (the user reviews and saves it), is rate-limited (10/hour per user) and audited as `strategy.ai_draft` with the description's length and the outcome — not the text. No account, balance or personal data is sent. |
| Configuration | No secrets in Git (`.env` ignored; `.env.example` files contain placeholders). `php artisan tp:keys` generates the shared secrets locally. |

## Operator checklist for production

* `APP_ENV=production`, `APP_DEBUG=false`, HTTPS, `SESSION_SECURE_COOKIE=true`.
* Engine: `APP_ENV=production` refuses to start without a 32+ char `ENGINE_API_SECRET` and a `BROKER_CREDENTIALS_KEY`.
* Back up `BROKER_CREDENTIALS_KEY` — losing it makes stored broker credentials unrecoverable (re-enter them).
* Keep the engine port private (loopback or private network).
